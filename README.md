# userdrv

BORUIX 的**用户态驱动模板**：演示一个驱动如何在用户态认领真实硬件、映射其寄存器并读写。

[English](README.en.md)

## 核心想法：驱动不必住在内核里

驱动放进内核有个代价：**内核里的一段代码出错，整个系统就崩了**。而驱动往往是内核中最庞大、最容
易出问题的部分。

本模板演示另一条路：**把驱动的实现搬到用户态，只把"访问硬件的权限"留在内核里**。

| 步骤 | 发生在哪 | 做什么 |
| --- | --- | --- |
| 登记 | 内核 | 声明"我要驱动这个设备" |
| 认领 | 内核 | 内核把该设备的硬件资源**授权**给这个进程 |
| 映射 | 内核 | 设备的寄存器空间被映射进该进程的地址空间 |
| 读写 | **用户态** | 驱动代码访问硬件寄存器 |

关键是最后一步：**驱动主体逻辑完全在用户态运行**。它出错只会让这个进程崩溃，内核和其他程序不受
影响。

本仓库**不是**一个真实驱动，而是**骨架**，演示完整调用序列：查询设备、登记、认领、映射、读寄存器。

## 两种模式

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| **瞬态** | 登记 → 认领 → 读一次寄存器 → 释放 → 退出 | 手动验证、演示 |
| **长驻** | 登记 → 认领 → **保持认领**，周期性读寄存器 | 自动装载、持续服务设备 |

长驻模式以**睡眠而非忙等**的方式等待，中间让出 CPU。紧紧盯着寄存器的忙等循环会白白占满一个核心。

## 被终止时会发生什么

长驻驱动可能被强制终止。若不处理，那个设备会处于"被一个已不存在的进程认领着"的状态——**谁也
用不了它**。

内核的处理是：进程退出时**自动隔离其认领**，释放设备。于是上层的管理程序可以重新拉起驱动，设备
重新可用——**驱动崩溃意味着"重启它"，而不是"设备永久失效"**。

## 权限

登记与认领设备是**受限操作**。以普通用户身份拉起时会收到"权限不足"并**如实报错退出**——能认领
硬件设备的程序可以直接操作硬件，不受普通文件权限约束，这个限制是必要的。

## 硬件读写必须用易失性访问

硬件寄存器**不是普通内存**。编译器优化普通内存访问的前提是"值不会自己变"，但寄存器的值会**被
硬件改写**。若被当成普通变量优化（例如把重复读取合并成一次），驱动就会读到过期的值。

易失性访问告诉编译器：**每次都要真的去读**。这是写驱动的基本功——在普通内存上正确的代码，用
在这里就是错的。

```bash
cargo build --release
```

## 文件结构

```
userdrv/
├── Cargo.toml    # 包定义
├── build.rs      # 注入链接脚本
├── linker.ld     # 用户态段布局
└── src/
    └── main.rs   # 两种模式的驱动骨架
```
